Connecting Hoymiles systems via OpenDTU

This page extends the Sigenergy architecture with a second system type. The display device, the software layers and the update process stay the same. What is new: a radio receiver next to the inverter and a second driver in the collector. As of 1 November 2026, based on the OpenDTU documentation.

How this page attaches to the base page. Sections 10, 11, 13 and 14 continue the numbering of the base page. Anything not repeated here (Balena, kiosk, Raspberry Pi, Wi-Fi setup) applies unchanged.

10Overview for Hoymiles

Hoymiles microinverters have no network port. They send their data by radio. A small module called OpenDTU receives the radio signal and makes the values available on the home network. OpenDTU pushes its values over MQTT to a small broker on our display device, and the collector subscribes to them. With Sigenergy the display queries the Energy Controller directly; here the values are delivered to it.

11What OpenDTU is and how it differs from Modbus

With Sigenergy, the device already speaks network. We query the controller directly and get an answer. A Hoymiles inverter speaks only radio, and in a format that only Hoymiles' own devices understand. Normally a Hoymiles DTU with a cloud connection handles this.

OpenDTU is open-source software for ESP32 microcontrollers that replaces this DTU. The module receives the radio data, stores it and publishes it over MQTT. It is the interpreter between radio and network. Which radio chip is needed depends on the inverter series: the HM series needs the NRF24L01+, the HMS and HMT series the CMT2300A.

13Data access: MQTT

OpenDTU can deliver its values over MQTT or through a JSON web API. We use MQTT: OpenDTU pushes updates to a broker on the display device, and the collector subscribes to them. The web API stays as a fallback.

MQTT

  • Per device: <serial number>/status/reachable, <serial number>/0/temperature, <serial number>/<1–4>/power

What MQTT means for the setup. The display device becomes the server: OpenDTU must know its address, so give it a fixed one (DHCP reservation); whether a hostname works instead is not checked. The broker should be protected with a login (OpenDTU's MQTT settings page was not checked for this). And if the display device is off, OpenDTU has nowhere to deliver its values.

14Software changes

The collector gets a driver layer. Each driver translates the language of one system type into the same data model. Everything behind it (SQLite, WebSocket, UI, kiosk) no longer knows any manufacturer. Adding another manufacturer later means adding another driver.

Driver interface (draft)

Sketch, untested. It shows what every driver has to deliver:

# collector/drivers/base.py
from dataclasses import dataclass
from typing import Protocol

@dataclass
class Sample:
    ts: float
    pv_power_w: float | None = None
    yield_day_wh: float | None = None
    battery_soc: float | None = None
    battery_power_w: float | None = None
    grid_power_w: float | None = None
    load_power_w: float | None = None
    online: bool = True      # device reachable on the home network
    asleep: bool = False     # inverter not reachable, e.g. at night

class Driver(Protocol):
    name: str
    async def discover(self) -> str | None: ...   # finds the system on the home network
    async def read(self) -> Sample: ...           # one measurement cycle
# collector/drivers/hoymiles_opendtu.py  (core, MQTT)
class HoymilesMqtt:
    def __init__(self, base: str):       # base topic as set in OpenDTU
        self.base, self.state = base, {}

    async def listen(self):              # runs in the background
        async with aiomqtt.Client("broker") as c:   # asyncio MQTT client
            await c.subscribe(f"{self.base}/#")
            async for m in c.messages:
                key = str(m.topic).removeprefix(self.base + "/")
                self.state[key] = m.payload.decode()

    async def read(self) -> Sample:
        s = self.state
        dtu_up = s.get("dtu/status") == "online"
        reachable = any(v == "1" for k, v in s.items()
                        if k.endswith("/status/reachable"))
        return Sample(
            ts=time.time(),
            pv_power_w=_num(s.get("ac/power")),      # _num: str -> float | None
            yield_day_wh=_num(s.get("ac/yieldday")),
            online=dtu_up,
            # night vs. radio problem: use time of day and <serial>/radio/rx_fail_*
            asleep=dtu_up and not reachable,
        )

Pairing via the broker

There is no network scan. OpenDTU is told the broker's address and the base topic once. The collector recognises the device as soon as its first messages arrive under that base topic.

Night is downtime

Without sun the inverter switches off. OpenDTU then reports "not reachable". That is not an error. The UI shows "System asleep" and the previous day's yield.

One fleet, one image

The driver is set per device in balenaCloud as a device variable. Hoymiles devices additionally run the broker as a fourth container. The update process and fleet from section 7 stay unchanged.
